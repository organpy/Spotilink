# SpotiLink v2

v2 adds playlist support, a `ytmusicapi` resolver and fallback, and persistent
background jobs. All v1 endpoints (`/v1/resolve`, `/healthz`, `/`) are unchanged.
SpotiLink only resolves metadata and URLs: it never downloads, converts, hosts
or proxies audio or video.

## Supported inputs

| Input | Extraction | Matching | Result |
|---|---|---|---|
| Spotify track | existing page extraction | YouTube Data API, then `ytmusicapi` fallback (SoundCloud kept) | synchronous `200` |
| Spotify playlist | Spotify web-player GraphQL (see [extraction results](v2-spotify-extraction.md)) | `ytmusicapi` only | job, `202` |
| YouTube playlist | `yt-dlp` flat extraction | none (URLs come from the playlist) | job, `202` |

Individual YouTube videos are rejected with `youtube_video_not_supported`. A
`watch?v=…&list=…` URL is a playlist when the list is a public playlist
(`PL…`, `OLAK5uy_…`, `UU…`, `FL…`). Mixes (`RD…`), Watch Later and Liked
videos are rejected. Only `open.spotify.com`, `youtube.com`, `m.`/`music.youtube.com`
and `youtu.be` are accepted; the submitted URL is never fetched, canonical URLs
are rebuilt from the validated ID.

## Endpoints

### `POST /v2/resolve`

```bash
curl -X POST https://spotilink.organfx.com/v2/resolve \
  -H 'content-type: application/json' \
  -d '{"url": "https://open.spotify.com/playlist/7EAqBCOVkDZcbccjxZmgjp"}'
```

Playlist → `202 Accepted` (+ `Location` header):

```json
{
  "type": "playlist",
  "source": "spotify",
  "job_id": "job_1RsijW4568udwWpq",
  "status": "queued",
  "reused": false,
  "status_url": "/v2/jobs/job_1RsijW4568udwWpq",
  "tracks_url": "/v2/jobs/job_1RsijW4568udwWpq/tracks"
}
```

`reused: true` means an active job, or a recent finished job for the same
playlist, was returned instead of creating a new one.

Spotify track → `200`: `{"type": "track", "source": "spotify", "resolution": {…}}`
where `resolution` is exactly the v1 `/v1/resolve` response body.

### `GET /v2/jobs/{job_id}`

```json
{
  "job_id": "job_1RsijW4568udwWpq",
  "status": "completed",
  "source": "spotify",
  "playlist": {
    "id": "7EAqBCOVkDZcbccjxZmgjp",
    "title": "Rolling Stone Magazine - 500 Greatest Songs of All Time (2024)",
    "reported_total": 594,
    "extracted_total": 594,
    "extraction_complete": true,
    "incomplete_reason": null,
    "truncated": false
  },
  "progress": {"processed": 594, "total": 594, "matched": 560, "uncertain": 34,
               "unmatched": 0, "unavailable": 0, "failed": 0, "pending": 0},
  "extractor": "spotify_downloader",
  "resolver": "ytmusicapi",
  "warnings": [],
  "error": null
}
```

Statuses: `queued`, `extracting`, `matching`, `completed`, `partial`, `failed`.

* `extraction_complete` says whether the **source playlist** was fully read
  (extracted count equals the count Spotify reports and was not cut by
  `PLAYLIST_MAX_TRACKS`). It is independent of matching quality.
* `completed` = fully extracted and every track was processed without provider
  failures. `partial` = the job finished but extraction was incomplete and/or
  some tracks `failed` (provider errors). Unmatched/uncertain tracks alone do not
  make a job `partial`.
* `warnings` lists extractors that failed before the successful one.

### `GET /v2/jobs/{job_id}/tracks?offset=0&limit=100`

`limit` is 1–500. Results are available while the job is running.

```json
{
  "job_id": "job_1RsijW4568udwWpq", "status": "matching",
  "offset": 0, "limit": 100, "total": 594, "next_offset": 100,
  "tracks": [{
    "position": 1, "source_id": "…", "spotify_id": "…",
    "title": "Respect", "artists": ["Aretha Franklin"], "duration_ms": 147000,
    "youtube_url": "https://www.youtube.com/watch?v=VIDEO_ID", "youtube_id": "VIDEO_ID",
    "confidence": 0.98, "provider": "ytmusicapi", "status": "matched",
    "match_title": "Respect", "match_artist": "Aretha Franklin", "detail": null
  }]
}
```

Track `status`:

| status | meaning |
|---|---|
| `pending` | not processed yet |
| `matched` | confidence ≥ `YT_MUSIC_MATCH_THRESHOLD` |
| `uncertain` | best candidate between the uncertain and match thresholds; `youtube_url` is the **suggestion**, not a confident match |
| `unmatched` | no acceptable candidate |
| `unavailable` | the source entry has no usable metadata (removed track, podcast episode, private/deleted YouTube video); `detail` has the reason |
| `failed` | provider error (throttling, timeout); retry later — never cached as "no result" |

Order and duplicates are preserved: a track listed twice appears twice, with its
original positions, and is searched once.

### `GET /v2/health`

Provider availability, circuit-breaker state, extractor chain and job limits.
It never returns credentials or tokens.

### Errors

All v2 errors use `{"ok": false, "error": {"code", "message", "retryable", "retry_after_seconds"}}`.

| HTTP | codes |
|---|---|
| 400 | `invalid_request` |
| 404 | `job_not_found` |
| 422 | `invalid_url`, `unsupported_input`, `youtube_video_not_supported`; Spotify track errors reuse the v1 codes |
| 429 | `rate_limited` (`Retry-After` set) |
| 503 | `queue_full`, `matcher_unavailable`, `playlists_disabled` |

Job failures appear in `GET /v2/jobs/{id}` as `status: "failed"` with
`error.code` one of `playlist_not_found`, `playlist_empty`, `upstream_blocked`,
`upstream_schema_changed`, `upstream_unavailable`, `job_interrupted`, `internal_error`.

## Single-track provider fallback

```
cache → Spotify metadata → circuit closed? → YouTube Data API ──match──▶ cache, return
                                  │ open / error / no match
                                  ▼
                              ytmusicapi ──match (same v1 threshold)──▶ cache, return
```

* The v1 response schema is unchanged; `match.platform` stays `youtube`. The
  backend is stored per cache row (`resolutions.provider`).
* **Circuit breaker**: an upstream quota/429 (or a rejected API key) opens the
  circuit for `PRIMARY_RESOLVER_COOLDOWN` seconds (longer if `Retry-After` is
  larger). While open, requests go straight to `ytmusicapi`. After the cooldown
  exactly one request probes the primary; success closes the circuit. The local
  token-bucket limiter does not open it. State is per process.
* Negative results are cached only when every provider that should have been
  asked completed its search.
* `ytmusicapi` is not unlimited. Throttling (HTTP 429/403) is reported as a
  provider rate limit and never cached.

## Matching (ytmusicapi)

For each Spotify track: shared-cache lookup → search `songs` → (if no
acceptable song) search `videos` → score every candidate → best candidate above
the threshold. Never "first result".

Score = title 45% + artist 35% + duration 20% (renormalised when a duration is
missing), plus a small bonus for artist-published songs/official videos, minus
penalties for version mismatches (remix, live, cover, karaoke, tribute,
slowed/sped-up, instrumental, acoustic, …; applied both ways, so a requested
remix matches a remix), and for non-official lyric uploads. Unicode (NFKD),
punctuation, case, featured-artist suffixes, delivery noise
("Official Video") and pure edition annotations ("- Remastered 2010",
"- Single Version") are normalised away. Hard gates: minimum title and artist
similarity, and a maximum duration difference.

## Jobs

* Stored in SQLite (`jobs`, `job_tracks`, `playlist_cache`). The 100 → 1000+
  track playlists are processed in the background with `PLAYLIST_MAX_CONCURRENT_JOBS`
  jobs at a time and `YT_MUSIC_CONCURRENCY` concurrent searches; synchronous
  libraries run in threads so the event loop is never blocked.
* Workers claim a job with a lease inside `BEGIN IMMEDIATE`; two uvicorn
  workers never process the same job. A heartbeat renews the lease. After a
  crash or restart the lease expires and the job resumes from its first pending
  track (already matched tracks are not redone). A job interrupted more than 3
  times is failed (`job_interrupted`).
* Bounded: `PLAYLIST_MAX_PENDING_JOBS` active jobs (then `503 queue_full`),
  `PLAYLIST_MAX_TRACKS` tracks per playlist (excess reported via
  `truncated` / `incomplete_reason: "max_tracks"`), per-client rate limit on
  `POST /v2/resolve`.
* Reuse: an active job, or a finished one younger than `PLAYLIST_CACHE_TTL`
  (complete) / `PLAYLIST_PARTIAL_CACHE_TTL` (incomplete), is returned instead of
  a new job. Failed jobs are never reused.
* Cleanup: jobs and their tracks are deleted `JOB_TTL_SECONDS` after they finish; the
  janitor runs every 10 minutes.
* Matching stops early (remaining tracks `failed`/`provider_unavailable`) after 8
  consecutive provider failures, so a throttled upstream isn't hammered.

## Configuration

See `.env.example`. Existing variables are unchanged.

| Variable | Default | Purpose |
|---|---|---|
| `YT_MUSIC_ENABLED` | `true` | ytmusicapi fallback + Spotify playlist matching |
| `YT_MUSIC_CONCURRENCY` | `3` | concurrent ytmusicapi searches |
| `YT_MUSIC_MATCH_THRESHOLD` / `_UNCERTAIN_THRESHOLD` | `0.75` / `0.60` | playlist matching |
| `PRIMARY_RESOLVER_COOLDOWN` | `300` | circuit-breaker cooldown (s) |
| `SPOTIFY_PLAYLIST_EXTRACTOR` | `auto` | `auto`, `spotify_downloader`, `webplayer` |
| `SPOTIFY_WEBPLAYER_FALLBACK` | `true` | try the second implementation |
| `SPOTIFY_EMBED_PARTIAL_FALLBACK` | `true` | last-resort partial data (≤100 tracks) |
| `PLAYLIST_MAX_TRACKS` | `1000` | hard cap per playlist |
| `PLAYLIST_MAX_CONCURRENT_JOBS` | `2` | jobs processed at once |
| `PLAYLIST_MAX_PENDING_JOBS` | `50` | queue bound |
| `PLAYLIST_CACHE_TTL` | `86400` | reuse window for complete playlists |
| `RESOLVER_CACHE_ENABLED` | `true` | use the shared resolution cache for playlists |
| `V2_RATE_LIMIT_PER_MINUTE` | `20` | per client, `POST /v2/resolve` |

## Known limitations

* Spotify extraction uses undocumented internal endpoints and may break without
  notice; see [extraction results](v2-spotify-extraction.md). Both
  implementations use the same upstream gateway, so if Spotify blocks it
  (HTTP 429/403) they fail together; the job then returns the ≤100-track
  embed data flagged `extraction_complete: false`, or fails with `upstream_blocked`.
  No proxies, CAPTCHA solving or evasion are attempted.
* Playlists Spotify generates per-user, private playlists and playlists
  without a public page are not reachable (`playlist_not_found`).
* The circuit breaker and rate limiters are per process.
* `ytmusicapi` and `yt-dlp` scrape YouTube's private APIs and can break after
  YouTube changes; upgrade them regularly (`uv lock --upgrade-package ytmusicapi yt-dlp`).
* Matching is heuristic. Always surface `uncertain` results as suggestions.

## Troubleshooting

| Symptom | Check |
|---|---|
| `matcher_unavailable` | `YT_MUSIC_ENABLED=true` |
| job `failed`, `upstream_schema_changed` | Spotify changed its GraphQL schema; see logs for the failing step; set `SPOTIFY_PLAYLIST_EXTRACTOR=webplayer` to switch implementation; update the code |
| job `failed`, `upstream_blocked` | Spotify/YouTube throttled the server IP; wait, don't retry in a loop |
| many `failed` tracks | ytmusicapi throttled; lower `YT_MUSIC_CONCURRENCY`; resubmit later (matched tracks are cached) |
| everything `uncertain` | lower `YT_MUSIC_MATCH_THRESHOLD` carefully; check `match_title`/`match_artist` |
| jobs stuck in `queued` | workers only run inside the API process; check logs and `PLAYLIST_MAX_CONCURRENT_JOBS` |
| `/v2/health` `circuit.state: open` | the YouTube Data API quota is exhausted; it re-probes automatically |
